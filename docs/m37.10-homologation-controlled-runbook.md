> **Regra Anti-Atalhos**: Não utilizar `supabase db push` indiscriminado (que aplicaria todo o lote de uma vez), não utilizar o SQL Editor manual descompassado do ledger, e não utilizar `migration repair` fictício.

Para cada migration $i \in \{1, 2, 3, 4, 5\}$, executar o ciclo fechado de controle:

#### Ciclo de Controle por Migration:

1. **Pré-Checagem de Ledger**:
   Confirmar que a versão não consta no ledger do Supabase:
   ```sql
   SELECT count(*) = 0 FROM supabase_migrations.schema_migrations WHERE version = '<VERSAO>';
   ```
2. **Aplicação com o Mecanismo de Migrations do Supabase**:
   Aplicar exclusivamente o arquivo da migration corrente dentro de transação atômica gerenciada:
   ```bash

   psql -X -v ON_ERROR_STOP=1 -1 -f "supabase/migrations/<ARQUIVO_MIGRATION>.sql"
   ```
3. **Registro no Ledger Oficial do Supabase**:
   Registrar formalmente no histórico oficial de migrations:
   ```sql
   INSERT INTO supabase_migrations.schema_migrations (version) VALUES ('<VERSAO>');
   ```
4. **Verificação de Catálogo Pós-Etapa**:
   - Confirmar que a função/tabela modificada foi criada com `owner = 'postgres'`.
   - Confirmar `search_path = ''` e `SECURITY DEFINER = true`.
   - Confirmar as ACLs esperadas (ex: `check_visit_promotor_update_integrity` com `{postgres=X/postgres}`).
   - Confirmar que a tabela `attendance_private.scheduled_recovery_authorizations` (na migration 5) tem acesso revogado de `PUBLIC, anon, authenticated`.
5. **Stop-Gate (Critério de Continuidade)**:
   - Se a etapa passar em todas as asserções: prosseguir para a próxima migration ($i+1$).
   - Se qualquer erro ocorrer: **PARAR IMEDIATAMENTE**. Não aplicar as migrations restantes.
