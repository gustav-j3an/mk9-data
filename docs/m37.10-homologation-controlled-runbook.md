### 1. Diagnóstico dos Riscos do Procedimento Anterior

A revisão técnica identificou que o procedimento anterior incorria em quatro riscos inaceitáveis:

1. **Manipulação Manual do Ledger (`INSERT` / `DELETE` direto)**:
   - Propor comandos `psql` manuais seguidos de `INSERT INTO supabase_migrations.schema_migrations` ou `DELETE FROM supabase_migrations.schema_migrations` desvincula a execução do DDL do mecanismo de rastreamento do Supabase.
   - Caso o DDL execute com sucesso mas o INSERT falhe (ou vice-versa), o banco entra em estado de inconsistência silenciosa entre o schema real e o ledger.
2. **Uso Indevido de `migration repair` ou SQL Editor**:
   - `migration repair` artificializa o histórico sem garantia de que os objetos correspondentes foram aplicados ou revertidos com fidelidade.
   - O SQL Editor é um canal manual propenso a desvios de execução, cortes de transação e ausência de versionamento automático no ledger.
3. **Falsa Premissa de Rollback Comprovado**:
   - Os testes aprovados no runner do GitHub Actions (PostgreSQL 17 descartável) comprovam a lógica SQL, a concorrência e as regras de negócio em ambiente sintético limpo.
   - Isso **não comprova** a reversibilidade nem a ausência de efeitos colaterais na base de homologação real (`tafjceemuetqjyngresg`), que possui histórico acumulado, usuários reais no schema `auth` e dados legados.
4. **Configuração de Migrations Desabilitada (`config.toml`)**:
   - O arquivo `supabase/config.toml` do repositório define `[db.migrations] enabled = false` devido ao histórico divergente de migrations legadas (Missões 26 e 28). O uso de comandos como `supabase db push` indiscriminado sem parametrização controlada falharia ou tentaria aplicar versões antigas não reconciliadas.

### 4. Protocolo Auditável de Recuperação e Rollback

Caso ocorra interrupção ou falha durante a janela de homologação, o rollback deve seguir estritamente as regras de segurança:

#### A. Proibição de Atalhos Manuais:
- **NÃO** executar `DELETE FROM supabase_migrations.schema_migrations` antes de comprovar o estado do catálogo.
- **NÃO** executar `supabase migration repair` como atalho cosmético.

#### B. Sequência de Restauração Auditada:
1. **Auditoria de Diagnóstico Preliminar**:
   Executar consulta somente leitura para identificar exatamente qual migration falhou e quais objetos foram criados ou alterados no catálogo.
2. **Restauração Fisiológica dos Objetos do Banco**:
   Executar o script de restauração das funções homologadas:
   ```bash
   psql -X -v ON_ERROR_STOP=1 -f "docs/m37.4-homologation-function-recovery.sql"
   ```
   *Efeito:* Restaura a definição original das três funções (`attendance_start_scheduled_occurrence`, `attendance_check_in` e `check_visit_promotor_update_integrity`), restaura os grants canônicos e remove com segurança a tabela transitória `attendance_private.scheduled_recovery_authorizations`.
3. **Conferência Estrutural do Catálogo**:
   Verificar formalmente com a consulta canônica de integridade:
   ```sql
   WITH expected(schema_name, function_name, expected_acl) AS (
     VALUES
     ('attendance_private','attendance_start_scheduled_occurrence','{postgres=X/postgres,authenticated=X/postgres}'),
     ('public','attendance_check_in','{postgres=X/postgres,authenticated=X/postgres,service_role=X/postgres}'),
     ('public','check_visit_promotor_update_integrity','{postgres=X/postgres}')
   )
   SELECT count(*) = 3 AND bool_and(pg_get_userbyid(p.proowner)='postgres'
     AND p.prosecdef AND p.proconfig = ARRAY['search_path=""']::text[]
     AND p.proacl::text=e.expected_acl
     AND NOT has_function_privilege('anon',p.oid,'EXECUTE')
     AND (e.function_name='check_visit_promotor_update_integrity' OR has_function_privilege('authenticated',p.oid,'EXECUTE')))
   FROM expected e JOIN pg_namespace n ON n.nspname=e.schema_name
   JOIN pg_proc p ON p.pronamespace=n.oid AND p.proname=e.function_name;
   ```
   *(Deve retornar `t` / true).*
4. **Reconciliação Auditada do Histórico de Migrations**:
   Somente após comprovação pericial de que os objetos foram revertidos e o catálogo retornou ao baseline pré-M30, registrar a conciliação do ledger conforme o procedimento oficial aprovado pelo DBA/administrador.
