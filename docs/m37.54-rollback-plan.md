# Plano de Rollback e Recuperação — Missão 37.52 / 37.54

## 1. Contexto e Objetivos de Segurança
A migration `20261108100000_m37_integral_weekly_recovery.sql` remove a constraint `visits_promotor_loja_industria_data_unique` e cria índices únicos parciais para acomodar múltiplas recuperações de datas programadas distintas no mesmo dia civil.

Se for necessário executar um rollback:
1. **Não basta** simplesmente executar `ALTER TABLE visits ADD CONSTRAINT visits_promotor_loja_industria_data_unique...`. Se o promotor tiver executado mais de uma recuperação no mesmo dia civil (ex: recuperou segunda e quarta no sábado), o PostgreSQL abortará com erro de chave duplicada violando a constraint antiga.
2. É mandatório ter um procedimento estruturado para reconciliação ou isolamento desses registros antes de qualquer alteração de schema.

---

## 2. Procedimento de Rollback Passo a Passo

### Passo 1: Inspecionar Registros Criados sob a Nova Regra
Executar consulta de auditoria para identificar se existem visitas concluídas com a mesma data efetiva para a mesma loja/indústria:
```sql
SELECT promotor_matricula, loja_codigo, industria_codigo, data_visita, count(*)
FROM public.visits
GROUP BY promotor_matricula, loja_codigo, industria_codigo, data_visita
HAVING count(*) > 1;
```

### Passo 2: Decisão de Negócio e Reconciliação
Caso existam registros múltiplos:
- As visitas concluídas representam trabalho de campo real já executado pelo promotor.
- Caso o rollback seja solicitado sem descartar o histórico de trabalho:
  - Manter as visitas em `visits` utilizando o índice parcial por ocorrência (`visits_promoter_route_scheduled_date_unique`), revertendo apenas a RPC para o comportamento restritivo anterior.
- Caso seja necessário restaurar rigorosamente a constraint legada:
  - Isolar as visitas secundárias em tabela de arquivo histórico antes de reintroduzir a constraint.

### Passo 3: Restauração da Versão Anterior da RPC
Reverter a função `attendance_private.attendance_start_scheduled_occurrence` para o snapshot auditado em `docs/m37.4-homologation-function-recovery.sql` (ou migration `20261107140000`), restabelecendo a trava de verificação no mesmo dia:
```sql
SELECT v.* INTO v_today_visit FROM public.visits v
WHERE v.promotor_matricula = v_matricula
  AND v.loja_codigo = v_route.loja_codigo
  AND v.industria_codigo = v_route.industria_codigo
  AND v.data_visita = v_effective_date
FOR UPDATE;

IF FOUND AND (v_existing.id IS NULL OR v_today_visit.id IS DISTINCT FROM v_existing.id) THEN
  RAISE EXCEPTION 'A visit for this store and industry already exists today' USING ERRCODE = '23505';
END IF;
```

### Passo 4: Restauração dos Índices / Constraints
Caso não haja colisões na tabela `visits`:
```sql
ALTER TABLE public.visits
  ADD CONSTRAINT visits_promotor_loja_industria_data_unique
  UNIQUE (promotor_matricula, loja_codigo, industria_codigo, data_visita);

DROP INDEX IF EXISTS public.visits_regular_promoter_store_industry_date_unique;
DROP INDEX IF EXISTS public.visits_promoter_store_industry_scheduled_date_unique;
```
