# Missão 37.8 — Reconciliação Definitiva da Recuperação de Visitas Pendentes

Documento de validação da **Missão 37.8**, corrigindo em definitivo o conflito de recuperação de visitas pendentes e não realizadas materializadas no banco de dados isolado da stack Supabase CLI 3.0.0 com PostgreSQL 17.11 no GitHub Actions.

---

## 1. Causa Raiz Definitiva

Na Missão 37.7, a tentativa de recuperar uma visita previamente materializada com `status='pendente'` (ou `'nao_realizada'`) e `scheduled_date` da data anterior apresentou um conflito estrutural entre duas guardas de segurança:
1. **Índice Único** `visits_promoter_route_scheduled_date_unique`: Proíbe a inserção de uma segunda linha na tabela `public.visits` para a mesma combinação de `(promotor_matricula, rota_id, scheduled_date)`.
2. **Trigger de Integridade** `public.check_visit_promotor_update_integrity`: Instalado como trigger `BEFORE UPDATE` em `public.visits`, proíbe expressamente que um promotor altere `data_visita` (`'Visit identity is immutable'`, SQLSTATE `42501`).

Quando o promotor tentava recuperar a ocorrência:
- A tentativa de chamar `attendance_check_in` criava uma nova linha para a data atual, mas ao tentar ajustar `scheduled_date` para a data original de ontem, colidia com a chave única (SQLSTATE `23505`).
- A tentativa de atualizar diretamente a linha existente alterando `data_visita` para hoje esbarrava no trigger de integridade, que bloqueia qualquer modificação de `data_visita` quando `auth.uid()` é o do promotor autenticado.

---

## 2. Investigação do Trigger na Homologação

- **Origem**: A função foi definida na migration base `20261022152449_mk9_date_visit_regularization_and_checkin_scope.sql`.
- **Assinatura**: `public.check_visit_promotor_update_integrity() RETURNS trigger`.
- **Propriedades**: `LANGUAGE plpgsql`, `SECURITY DEFINER`, `SET search_path = ''`.
- **Owner**: `postgres`.
- **ACLs / Permissões**: `REVOKE ALL ON FUNCTION public.check_visit_promotor_update_integrity() FROM PUBLIC, anon;`
- **Trigger**: `trg_visit_promotor_update_integrity BEFORE UPDATE ON public.visits FOR EACH ROW EXECUTE FUNCTION public.check_visit_promotor_update_integrity();`
- **Proteções Existentes**:
  - Visitas já iniciadas (`started_at IS NOT NULL`): bloqueia alteração fora do dia operacional corrente (`is_visit_in_current_operational_day`) e bloqueia qualquer mutação em `started_at`.
  - Visitas fechadas (`concluida`, `nao_realizada`): completamente bloqueadas para atualização direta por promotor.
  - Visitas regularizadas: protegidas contra alteração de status ou remoção de resolução administrativa.
  - Visitas pendentes: permite apenas transição para `em_andamento` na mesma `data_visita` original.

---

## 3. Avaliação das Alternativas e Solução Escolhida

### Alternativa A (Escolhida) — Conciliação no registro existente com autorização transacional estrita
- Em vez de criar um segundo registro, a visita pendente ou não realizada (sem regularização e sem evidências prévias) tem seu atendimento iniciado na própria linha existente.
- A autorização para a transição é concedida **exclusivamente no servidor** através de uma tabela interna não exposta: `attendance_private.scheduled_recovery_authorizations`.
- Como o schema `attendance_private` tem acesso revogado para `PUBLIC`, `anon` e `authenticated`, nenhum cliente externo consegue criar ou forjar autorizações via PostgREST.
- O trigger `check_visit_promotor_update_integrity` verifica e consome (faz `DELETE`) imediatamente a autorização no momento do `UPDATE` dentro da mesma transação atômica.
- Qualquer tentativa de `PATCH /rest/v1/visits` direto continua terminantemente bloqueada com SQLSTATE `42501`.

### Alternativa B (Descartada) — Preservar a pendência original e criar execução vinculada
- Descartada porque criaria linhas duplicadas para a mesma rota semanal, violaria o índice único `visits_promoter_route_scheduled_date_unique` (ou exigiria enfraquecê-lo), distorceria indicadores operacionais e exigiria alterações profundas em relatórios, fichas e histórico do Portal.

---

## 4. Detalhes da Implementação

Criada a migration incremental:
`supabase/migrations/20261107140000_m37_reconcile_materialized_pending_recovery.sql`

A migration implementa:
1. `attendance_private.scheduled_recovery_authorizations`: tabela interna com RLS habilitada e permissões revogadas de `PUBLIC`, `anon` e `authenticated`.
2. `public.check_visit_promotor_update_integrity()`: atualizada para validar a autorização transacional antes de permitir a alteração de `data_visita` para início de recuperação de ocorrência pendente/não realizada unicamente se:
   - For uma ocorrência sem início (`started_at IS NULL` e `completed_at IS NULL`);
   - Sem resolução administrativa (`regularization_status IS NULL`);
   - Sem checklist ou fotos prévias;
   - Mantendo idênticos promotor, loja, indústria e rota;
   - Transicionando estritamente para status `'em_andamento'` com `started_at` atual.
3. `attendance_private.attendance_start_scheduled_occurrence()`: atualizada para registrar a autorização atômica em `attendance_private`, atualizar a ocorrência pendente materializada existente e emitir a auditoria em `public.visit_schedule_actions`.

O script de recuperação em caso de emergência (`docs/m37.4-homologation-function-recovery.sql`) e a suíte de testes de catálogo (`scripts/m37-recovery-postgres17.sh`) foram atualizados para restaurar as três funções ao estado original de homologação e remover a tabela interna, assegurando reversão 100% idêntica se necessário.

## 6. Separação de Ambientes: Isolado vs Homologação

| Dimensão | Comprovado no Supabase Isolado | Depende de Teste na Homologação |
|---|---|---|
| Reconciliação de pendência materializada | Comprovado integralmente via GoTrue e PostgreSQL 17 | Não |
| Proteção contra PATCH REST arbitrário em `data_visita` | Comprovado integralmente via PostgREST local | Não |
| Concorrência de duas sessões com locks reais | Comprovado integralmente com advisory locks transacionais | Revalidar sob latência de rede externa |
| Restauração do catálogo e rollback | Comprovado via snapshot de catálogo e script de recuperação | Revalidar no preflight somente leitura |
| Migrations M18 (legado) | Não presentes no baseline do GitHub Actions | Sim (verificar compatibilidade na homologação) |
| Integridade com dados reais de promotores | Não aplicável (somente dados sintéticos) | Sim (validação com promotores de teste em homologação) |
